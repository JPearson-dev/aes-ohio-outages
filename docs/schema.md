# AES Ohio Outage Data Architecture & Schema

This document outlines the data source, upstream XML format, and the normalized schemas generated by this repository's scraping pipeline.

---

## 1. Upstream Data Source

- **Endpoint**: `https://myprofile.aes-ohio.com/DATA/DPLOMSDATA.xml`
- **Format**: XML (`<Incidents>` root element)
- **Refresh Frequency**: The utility updates this file approximately every 15 minutes.
- **Context**: This is the unauthenticated endpoint queried directly by AES Ohio's official outage map dashboard (formerly Dayton Power & Light / DP&L).

---

## 2. Upstream XML Structure

The raw XML file contains three distinct child elements under the root `<Incidents>`:

```xml
<Incidents>
  <!-- Individual incident markers (0 to hundreds) -->
  <Markers>
    <LAT>39.94702448</LAT>
    <LNG>-84.0257880732199</LNG>
    <TOTALCUSTS>1</TOTALCUSTS>
    <INCIDENTID>1807441</INCIDENTID>
    <IND>D</IND>
    <COUNTY>CLARK</COUNTY>
    <total>5498</total>
    <OutageTime>09/05/2026 09:26 AM</OutageTime>
    <EstimateTime>09/06/2026 01:30 AM</EstimateTime>
  </Markers>

  <!-- Pre-aggregated county totals (~24 counties) -->
  <Counties>
    <County>MONTGOMERY</County>
    <TotOut>5384</TotOut>
  </Counties>

  <!-- Overall status and broadcast alerts (1 record) -->
  <Message>
    <UMTime>null</UMTime>
    <UMessage>null</UMessage>
    <TotalOut>5495</TotalOut>
    <Outageat>9/5/2026 8:35:32 PM</Outageat>
  </Message>
</Incidents>
```

### Upstream Quirks & Inferred Fields
1. **`UMessage` and `UMTime`**: Inferred to represent **Utility Message** (or User Message) and its posting timestamp. During severe storm events or IT maintenance, outage map dashboards display a prominent banner across the top of the map. During normal operations, both elements contain the literal string `"null"`. Note: This expansion is an inference based on outage dashboard conventions, not official AES Ohio API documentation.
2. **Missing County Fields**: In some incidents (e.g. border areas or unassigned circuits), the `<COUNTY>` tag is completely omitted.
3. **String Literals for Null**: Null values appear as literal `"null"` strings (e.g., `<EstimateTime>null</EstimateTime>`, `<UMessage>null</UMessage>`).
4. **Duplicate Totals**: Each `<Markers>` entry includes a `<total>` tag duplicating the utility-wide count.
5. **Naive Timestamps & Timezones**: Timestamps are naive local clock times (America/New_York) without time zone offsets (`09/05/2026 09:26 AM` and `9/5/2026 8:35:32 PM`). Consequently, during the annual autumn Daylight Saving Time "fall-back" transition (when 2:00 AM becomes 1:00 AM), the 1:00 AM–1:59 AM hour repeats without EDT vs. EST disambiguation in the raw data.

## 3. Repository Architecture & Branch Separation

To preserve clean Git version history and prevent repository bloat:

- **`main` Branch**: Contains application source code, parsing scripts, GitHub Actions workflows, templates, documentation, and the future UI.
- **`data` Branch**: An orphan branch dedicated exclusively to dataset snapshots.
- **Local `.data-branch/` Worktree**: Locally, the `data` branch is checked out into `.data-branch/` (ignored by Git on `main`). This shares the `.git` database with zero duplicate repo storage.

---

## 4. Normalized Output Layout & Schema (`data` Branch)

The `data` branch organizes cumulative records at the root, and ephemeral rolling snapshots in a `current/` subdirectory:

```txt
data branch
├── README.md              <-- Explains the branch for visitors
├── heartbeat.csv          <-- Cumulative historical time series
└── current/
    ├── incidents.json     <-- Current active incident markers
    ├── counties.json      <-- Current county rollups
    ├── status.json        <-- Current metadata and totals
    └── latest.xml         <-- Raw XML payload for auditability
```

### `heartbeat.csv`
An append-only time-series log at the root of the branch, designed for rapid charting on the frontend without querying commit histories or parsing JSON diffs.
- **Strict Chronological Monotonicity**: Rows are appended only if the incoming `timestamp` is strictly newer than the most recent CSV entry (`current_dt > last_logged_dt`). Older samples or duplicate polls will never append duplicate rows.

```csv
timestamp,total_customers_affected,incident_count
2026-09-05T20:35:32,5495,399
2026-09-05T21:35:32,4911,392
```

**Decision: kept as a single flat file, not split into per-year/month folders.** At 15-minute polling that's ~96 rows/day and ~30 bytes/row — roughly 1MB/year, staying well under 10MB for a decade if cadence never changes, so there's no realistic future where file size burdens fetch time, diff size, or repo bloat. The main motivation for splitting — letting a human glance at the file and see what happened recently — is served by the `data` branch's commit history, the Actions run history, or `current/status.json`'s `updated_at` field, none of which require reshaping this file.

### `current/incidents.json`
The active list of incident markers.
- **Deterministic Sorting**: Sorted by `id` ascending so Git diffs only reflect actual grid changes (new, resolved, or customer count changes).
- **ISO 8601 Timestamps**: Converted to standard `YYYY-MM-DDTHH:MM:SS` strings.
- **Null Safety**: Missing `<COUNTY>` tags and `"null"` strings are standardized to JSON `null`.

```json
[
  {
    "id": 1805496,
    "lat": 39.65811727,
    "lng": -84.1710352554646,
    "customers_affected": 2,
    "county": "MONTGOMERY",
    "indicator": "D",
    "outage_time": "2026-09-04T14:01:00",
    "estimate_time": null
  }
]
```

### `current/counties.json`
County rollups sorted alphabetically by `county`.

```json
[
  {
    "county": "CLARK",
    "customers_affected": 10
  },
  {
    "county": "MONTGOMERY",
    "customers_affected": 5384
  }
]
```

### `current/status.json`
A lightweight snapshot of the latest poll state, total customers affected, incident count, and any alert messages broadcast by AES Ohio.

```json
{
  "updated_at": "2026-09-05T21:35:32",
  "updated_at_raw": "9/5/2026 9:35:32 PM",
  "total_customers_affected": 4911,
  "incident_count": 392,
  "utility_message": null,
  "utility_message_time": null
}
```

### `current/latest.xml`
The exact raw XML payload from the latest poll, saved for auditability and verification.

## 5. Local Development & Safeguards

### Safe Offline Testing with Samples
Running with `--sample` automatically redirects output to `./test-output/` (which is git-ignored) unless an explicit `--out-dir` is provided. This prevents sample data from contaminating the real `.data-branch` worktree:
```bash
python3 scripts/fetch.py --sample sample-data/DPLOMSDATA.xml
```

### Fetching Live Data Locally
To update the local worktree files without creating Git commits:
```bash
./scripts/update-data.sh
```

To explicitly commit changes to `.data-branch`:
```bash
./scripts/update-data.sh --commit
```

### Inspecting Local Data Branch History
```bash
git -C .data-branch log --oneline -n 5
git -C .data-branch diff HEAD~1 HEAD
```
